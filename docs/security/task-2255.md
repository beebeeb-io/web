## Corrected L9 (Claude lane w2255, 2026-10-28)

Built to the lead's "L9 correction" in the task file (workspace #236), against local core 28ab5d9. The vendored WASM was built on the testrig from that source; `beebeeb_wasm_bg.wasm` sha256 is 756eb00a…9379 in both trees. Its public API delta is exactly one swap: `verifyLegacyFolderKey` out, `openLegacyInviteOwnerCopy` in.

- `findExistingFolderKey`:
  - the newest active blob that opens wins: the purpose-bound format on its own, or a LEGACY copy only through core's `openLegacyInviteOwnerCopy`. That is ONE worker call per legacy blob, given ALL of the folder's rows verbatim. Core refuses text candidates, takes any row, checks each id once, and examines at most 64;
  - rows are fetched once, from the newest active invite, and only when a legacy blob needs proof;
  - when active invites exist and none opens with proof, it THROWS FOLDER_KEY_UNVERIFIED and never mints, so no split key. With no active invite it returns null and the caller mints, as before.
- `decryptOwnerFolderKey` (approval): the same rule for THIS invite's copy. It never substitutes another invite's key.
- Web holds no unproven candidate and derives no wrapping key: `deriveFileKey`/`decryptChunk`/`listFilesPage`/`zeroize` left the owner-copy ports.
- New invites always write the purpose-bound copy, so a proven legacy key is upgraded.
- The `folderKeyId` doc comment no longer claims the server enforces the key id.

Residuals (named, not fixed): **attack B** (a server that knows the folder's name key can forge a legacy copy that passes), **P3-3** (no key version), and **recipient public keys are not pinned** (a key-transparency issue, separate task). Availability: the server can always force FOLDER_KEY_UNVERIFIED, for example with no rows or 64 non-proving rows first. An empty legacy folder with active legacy invites can't be re-shared, or its pending invites approved, until those invites are removed. The message says so. That is a refusal, never a split.
